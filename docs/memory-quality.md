# 기억 추출과 검색 품질 개선 — 2026-11-04

## 챕터 13: 승인 전 후보의 정확성

수집 원문과 재사용할 기억 후보는 별개다. 기존 분류기는 `해줘`/`please` 같은 단어만 있어도
전체 메시지를 일반 feedback으로 잘라 저장했다. 질문·인용·일회성 요청에도 후보가 생겼고,
여러 조건을 한 key에 섞거나 4,000자 뒤의 예외/부정을 잘라낼 수 있었다.

현재 분류기는 명시한 언어, 어조, 형식, 대상, 예산, 기한, 브랜드, CTA를 안정된 key로 분리한다.
간단한 한국어/영어 답변 언어만 정규화하고 나머지는 원래 조건 문장을 값으로 보존한다.
금액/단위/기간/상한/부정을 요약하며 잃지 않는다. 문장별 발췌와 전체 원문 캡처 참조를 유지한다.
같은 key의 변경도 후보이며, 기존 확정 기억을 바꾸려면 명시적 대체 승인이 필요하다.

질문, 인용/예시, 조건부·미확정, 일회성 발언은 자동 후보 추출에서 제외한다. 코드 블록/인용 행도
제외한다. 분류되지 않은 단순 실행 요청은 기억으로 남발하지 않는다. 제한적으로 명시된 지속
피드백은 일반 후보로 남긴다. 서로 다른 조건이 너무 많거나 문장이 너무 길면 임의 절단하지 않고
후보 생성을 보류한다(32개 문장/8개 후보/후보 4,000자). 원문은 기존 캡처 제한 안에서 보존한다.

이것은 보수적인 로컬 규칙이며 일반 자연어 이해가 아니다. 조건부 표현이 섞인 메시지 전체를
보류할 수 있고, 새로운 표현은 누락될 수 있다. 모든 후보는 프로젝트 범위/미승인 상태이며
공통 자동 승격, 자동 확정, 외부 AI 전송, 기존 저장 기억의 자동 재분류는 없다.
상태 v4/envelope v1/v2는 바꾸지 않는다.

`npm run test:extraction`으로 개발용 합성 44발언을 재현한다. 구현 전/후 동일한 22개 양성
발언의 정확한 조건 key 분류는 2→22, 22개 음성 발언의 후보 오탐은 17→0이다. 부정·상한·출처,
상충하는 후보 승인과 원문 보존을 별도 회귀 검사한다. 개발에 사용한 사례이므로 실사용 정확도나
미지의 표현에 대한 일반화 수치로 해석하지 않는다. 실제 사용자 자료는 동의 후 별도 평가가 필요하다.

## 챕터 14: 표현 연결과 검색 비용

기존 어휘/BM25 검색에 8개 조건(language/tone/format/audience/budget/deadline/brand/cta)의
제한된 한국어·영어 질의 패턴을 추가한다. 예를 들어 `얼마까지 쓸 수 있지`는 budget,
`독자가 행동하게 만드는 문구`는 cta, `by when should we deliver`는 deadline에 연결한다.
문자·조사 정규화와 주제명 별칭은 후보 추출과 같은 어휘 정의를 사용한다.

개념 보조는 승인 기억의 정형 key(또는 `campaign.budget` 같은 마지막 구성요소)에만 적용한다.
기존 일반 feedback을 자동 재분류하지 않고 프로젝트를 추측하지도 않는다. 일반 feedback은
계속 어휘 검색으로 찾을 수 있다. 출처/변경 사유를 개념의 근거로 사용하지 않는다.
공통을 먼저 검색하고 선택된 프로젝트 하나만 추가 검색하며, 현재 요청/프로젝트 덮어쓰기와
승인 상태 필터를 점수 계산 전에 적용한다. 복수 프로젝트 트리거도 기존 선택 규칙을 유지한다.

`matchedTerms`와 새 `matchedTopics`가 단어/조건 일치 근거를 구분한다. 어휘 점수에 개념 일치
보조 점수를 더하며 `score`를 정답 확률로 해석하지 않는다. 반환한 값은 금고의 실제 승인 값이다.
평문을 서버나 외부 모델로 보내지 않고 색인도 RAM에만 둔다. 임베딩·범용 의미 검색은 아니다.
문장 속 한 글자만으로 엉뚱한 기억을 찾는 경우도 억제한다(단독 한 글자 질의는 기존대로 지원).

검색마다 공통/프로젝트의 전체 Map을 반복 복제하던 작업을 제거했다. 역색인으로 찾은 후보에
대해서만 key 덮어쓰기와 현재 요청을 검사한다. `get_context` 전체 조건 조립과 쓰기/암호화 저장의
비용은 이 최적화와 별개다. 승인·대체·사용 중지 후 무효화와 잠금 시 색인 수명은 유지한다.

`npm run test:retrieval`은 구현 전 구성한 합성 45개 양성/15개 음성 corpus를 평가한다.

| 지표 | 챕터 12 색인 | 챕터 14 색인 |
| --- | --- | --- |
| 첫 결과 적중 | 15/45 | 43/45 |
| 상위 5개 적중 | 15/45 | 43/45 |
| 음성 질의의 결과 노출 | 0/15 | 0/15 |
| 5,000개 짧은 기억의 검색 중앙값 | 0.64~0.70ms | 0.022~0.038ms |
| 같은 측정의 p95 | 0.94~2.64ms | 0.072~0.109ms |

성능은 동일 실행기에서 준비 후 100회씩 5회 측정한 동기 엔진 호출이다. IPC/디스크 쓰기/실제
클라이언트 응답 시간은 포함하지 않는다. 최초 색인 포함 조회는 약89→75ms였다. 실제 제품의
성능 보장이 아니다. 기존 17개 합성 corpus도 15→17개로 개선됐지만 확대 corpus를 우선한다.

`돈줄의 굵기를 정했던 값`, `사람 마음을 움직일 마지막 한 방` 같은 비유는 여전히 못 찾는다.
일반적인 부정·복합 의도 분석이나 임의 분야의 동의어 이해도 보장하지 않는다. 실제 사용자 평가와
기기 내 임베딩을 통한 의미 검색은 별도 후속 작업이다. 이 개발용 평가 수치를 실제 사용자 정확도나
MVP 실제 AI 개인화 성공으로 대체하지 않는다.

## 회차 3 추가 검증 (챕터17)

`예산: 50만원` 다음 줄의 `부가세 포함이고 월 단위야`처럼 비정형 부가 조건이 분리되어
빠지는 사례를 재현했다. 다문장에 독립 분류가 안 되는 절이 있으면4000자 이내 전체를
하나의 프로젝트 feedback 후보로 보존한다. 명시적인 정형 조건끼리만 안전하게 분리한다.
질문/인용/코드/한도 초과가 섞인 발언은 부분 조건을 저장하지 않고 원문 수집만 보존한다.
새 자동확정은 없으며, 복합 발언의 정형 검색 적중률보다 조건 보존을 우선한다.

100개(금액4×분리기호4×부가조건5) 생성 사례와 구체4사례, 기존 추출44발언 회귀 통과.
별도32seed×60명령=1920개의 승인/반려/대체/사용중지 시퀀스를 단순 사용자 의도 장부와
비교했다. 매 명령에서 공통/두 프로젝트의 맥락·검색ID와 현재요청 덮어쓰기, 주기적 재개와
fork격리를 검증했다. 신규 테스트 라이브러리 없이 기존 Node runner 사용. 일반 언어 이해
정확도나 실사용 전수검사가 아니라 재현 가능한 상태 불변식 검사다.
