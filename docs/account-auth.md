# 계정 인증 계약과 검증 화면

챕터 33은 보드 작업 명세의 **Supabase/SMTP 연결 전 상태 머신·폼·모의 제공자 검증 범위**를 구현한다. 실제 회원가입, 이메일 발송, Supabase 세션 검증이 완료된 것은 아니다. 현재 제품 `account-provider.js`는 미연결이며 계정 화면의 입력과 제출을 비활성화한다. 운영 사용자에게 모의 로그인 성공을 보여주지 않는다.

`src/account-auth.ts`의 `AccountProvider`는 가입, 이메일 확인, 로그인, 세션 갱신, 로그아웃, 재설정 요청/확정 경계를 정의한다. 상태에는 확인된 계정 ID·이메일·만료 시각만 담으며 토큰·비밀번호는 담지 않는다. 실제 제공자는 토큰 저장/갱신/철회와 서버 인증을 책임져야 한다. UI 상태나 클라이언트가 보낸 ID를 서버 권한의 근거로 삼으면 안 된다.

상태는 미연결, 로그아웃, 이메일 확인 대기, 로그인, 재설정 요청으로 나뉜다. 미인증 계정은 로그인되지 않고, 만료 시 계정 표시를 지운다. 요청을 직렬화하며 늦은 로그인 응답이 그 뒤의 로그아웃을 되돌리지 않는다. 외부 제공자의 오류 문자열을 화면이나 상태에 그대로 노출하지 않는다.

`extension/account.html`은 접근 가능한 입력·상태·실패·비활성 화면을 제공한다. 제출/화면 전환 시 비밀번호와 코드를 지우고 localStorage/sessionStorage에 저장하지 않는다. 브라우저 내부 문자열의 즉시 보안 소거를 보장하지 않는다. `extension/account-auth.js`는 TypeScript 원본에서 `npm run build`로 생성하며 릴리스 전 원본과 일치 여부를 검사한다.

## 금고와 분리

- 계정 비밀번호는 로컬 금고 비밀번호가 아니다. 계정 비밀번호로 금고 키를 파생하거나 자동 잠금 해제하지 않는다.
- 계정 비밀번호 재설정은 로컬 기억과 데이터 키를 변경하지 않는다. 금고 비밀번호 분실은 별도의 복구 파일/암호문 백업 흐름을 사용한다.
- 계정 인증 API·확인 코드·비밀번호를 MCP나 native broker에 추가하지 않는다. 계정 로그인이 기억 후보 승인이나 다른 프로젝트 접근 권한을 만들지 않는다.
- 생성된 오래된 스펙의 토큰 콘솔/LocalStorage 노출, 재설정 시 새 금고 salt/키로 데이터 유실, 자체 클라이언트 비밀번호 해시 프로토콜은 적용하지 않았다. 실제 연결 시 공식 인증 SDK의 검증된 HTTPS 계약을 사용하고 금고 자격증명은 보내지 않아야 한다.

## 증거와 남은 연결

테스트 전용 `test/support/mock-account-provider.mjs`는 메모리 내 서비스, salt+scrypt 비밀번호 검증, 만료·일회용·용도 구분 확인 코드, 별도 합성 메일함을 제공한다. 실제 이메일이나 프로덕션 백엔드가 아니다. 테스트에서만 주입하며 확장 배포물에 포함하지 않는다.

Node와 실제 Chromium에서 가입→미인증 로그인 거절→코드 확인→로그인/갱신→로그아웃→재설정→옛 비밀번호 거절, 코드 재사용/만료, 늦은 로그인 응답, 비밀 미저장, 금고 불변을 검증했다. 1280px/320px 화면을 확인했다.

실제 연결에는 기존 Supabase 프로젝트의 안전한 연결 설정, 인증 리다이렉트/메일 설정, 현재 스키마/RLS 읽기 전용 확인과 두 계정 간 허용/거절 증거가 필요하다. 기존 프로젝트를 초기화하거나 초기 SQL을 재실행하지 않았다.
