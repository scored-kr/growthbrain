사업성 검토에서 보완 우선순위는 기능 수보다 **첫 가치까지의 거리**다. 동의 없이 기억을 자동 확정하는 방식으로 그 거리를 줄이면 제품의 신뢰 조건을 깨뜨린다.

## 시장 대안과 차별화

2026-11-04 확인한 공식 문서에서 [ChatGPT Projects](https://help.openai.com/en/articles/10169521-projects-in-chatgpt)는
프로젝트 기억과 프로젝트 한정 기억을 설명한다. [Claude의 검색·기억](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context)도
프로젝트별 기억을 설명한다. 따라서 “기존 AI는 기억하지 않는다”는 전제는 쓰면 안 된다. 기능·플랜·배포 상태는 바뀔 수 있고 실제 고객 계정에서 비교해야 한다.

Growth Brain의 검증할 차별화는 **AI가 달라져도 사용자가 승인한 최신 조건과 출처가 유지되고, 잘못된 과거 조건을 멈출 수 있는가**다.
이는 아직 고객 비교 실험으로 입증되지 않았다. 프로젝트 지침 파일·재사용 브리프도 대안이다.
현재 공통→프로젝트 색인과 버전·폐기 처리는 기술적 토대다. 임베딩 추가가 구매 이유나 정확도 개선을 자동 보장하지 않는다.
먼저 실제 실패 질의를 익명·동의하에 분류한 후 어휘 검색·동의어·의미 검색 중 어떤 변화가 필요한지 판단한다.

## 첫 고객 가설과 현재 제품의 간극

사용자 추가 우선순위: **맥락 인계가 제품의 핵심**이다. 따라서 비교 실험은 단순한 말투·선호도 재현이 아니라
“다음 세션/다른 AI가 목표·결정 이유·완료 범위·미해결 문제·다음 행동을 이어받아 재설명 없이 다음 작업을 수행하는가”로 바꾼다.
현재 `get_context`는 승인된 key/value와 출처·이유·대체 관계를 전달하고 `goal`도 저장할 수 있다.
하지만 작업 완료/진행/차단/다음 행동을 독립적으로 검증하는 인계 스키마·최신성·완료 증거 확인은 아직 전용 구현이 없다.
원문을 수집하는 것과 정확한 인계 문서를 자동 구성하는 것은 별개다. 따라서 **맥락 인계 전체가 완성됐다고 표시하지 않는다.**

우선 추가할 제품 합격 사례: 세션 A가 목표·승인된 결정/이유·완료 항목·차단·다음 행동을 남김 →
사용자 검토 후 세션 B가 공통 맥락을 먼저 읽고 해당 프로젝트만 조회 → 이미 끝난 작업을 반복하지 않고 다음 작업 수행.
상충·오래된 상태·미승인 AI의 완료 주장·다른 프로젝트 상태는 현재 사실로 쓰지 않아야 한다.
장기 선호도와 작업 인계 상태의 생명주기는 다르므로, 인계 최신성/대체 규칙과 출처를 설계한 뒤 구현해야 한다.
이 검증은 실제 AI 호출과 결과물 증거가 있어야 완료되며 수동 복사나 합성 테스트만으로 통과 처리하지 않는다.

| 후보 | 예상 반복 문제(가설) | 현재 흐름과의 간극 |
| --- | --- | --- |
| 여러 고객을 담당하는 프리랜서·소규모 마케터 | 고객별 톤·예산·채널·금지사항을 매번 재설명 | 실제 사용하는 AI가 브라우저 중심이면 Codex/터미널 설치가 큰 장벽 |
| AI를 자주 쓰는 사업자 전반 | 전략·운영 맥락 재사용 | 업무·보안·사용 빈도가 너무 달라 하나의 MVP 기준을 잡기 어려움 |
| Codex/Claude Code를 쓰는 개발자·기술 프리랜서 | 저장소별 결정·개인 선호도 재사용 | 기술적 연결은 가깝지만 프로젝트 지침과 기본 기억으로 충분할 수 있음 |

권고하는 **첫 실험 가설**은 여러 고객 프로젝트를 오가는 프리랜서·소규모 마케터다. 시장 확정이나 개발자로의 자동 타깃 변경은 아니다.
기존 4명에게 사용 도구·지난 2주의 반복 문제·고객 수를 확인해서 이 가설이 맞지 않으면 수정한다.
Codex 한 클라이언트의 실제 흐름을 먼저 끝내라는 기존 요구는 유지한다. 다만 그 성공을 마케터의 구매 의사 검증으로 계산하지 않는다.
Chrome 수집 성공 역시 웹 AI가 제품 MCP를 호출하는 성공과 다르다. 대상 클라이언트의 실제 MCP 지원·설치 환경을 별도로 확인해야 한다.

## 전략 반론과 중단 기준

아래 순서는 실패 영향·현재 불확실성·저렴한 검증 가능성을 함께 고려했다. 기준은 파일럿용 **제안된 의사결정 규칙**이며 통계적 시장 추정이 아니다.

| 순위 / 핵심 가정 | 가장 강한 반론 | 가장 싼 검증 | 통과 / 실패 시 조치 |
| --- | --- | --- | --- |
| 1. 기존 기능보다 중요한 문제가 있다 | 브리프 한 장·AI 기본 프로젝트로 이미 충분함 | 실제 인터뷰 4명의 최근 실패 사례와 기존 해결법 확인. 가능하면 기존 방식과 동일 작업 비교 | 반복 문제와 비용이 구체적이지 않으면 세그먼트·문제를 다시 좁힘 |
| 2. 사용자가 첫 가치에 도달한다 | 로컬 설치와 MCP 연결이 고객 도구와 맞지 않음 | 합성 프로젝트로 5명 설치 관찰; 개입 횟수·시간·실제 MCP 호출·조건 반영 기록 | 제안: 3명 이상이 15분 이내 도움 없이 도달. 미달이면 기능 확대보다 설치 흐름 수정 |
| 3. 지속적인 순이익이 있다 | 후보 검토와 오검색 수정이 시간을 더 씀 | 2주 파일럿, 승인 시간과 설명/재작업 절약 시간을 함께 일지 기록 | 제안: 3/5가 서로 다른 3일 이상 자발적 사용하고 순절약이 양수. 미달이면 반복 업무·검토 흐름 수정 |
| 4. 위험을 통제할 수 있다 | 다른 고객의 조건이 섞이거나 폐기한 결정이 재등장하면 비용이 큼 | 서로 충돌하는 두 프로젝트, 수정·폐기·잠금·복구 시나리오 실제 기기 검사 | 범위 누출·폐기 부활 1건이라도 나오면 해당 흐름 확대 중단 및 수정. 발생 0건도 무위험 보장은 아님 |
| 5. 비용을 내고 쓸 이유가 있다 | 관심은 있지만 별도 구독은 원치 않음 | 가격을 명시한 유료 파일럿 제안과 실제 선택 기록(사용자가 진행) | 제안: 2/5 실제 유료 참여를 탐색 신호로 삼음. 의향 응답만으로 통과하지 않음 |

문제를 잘 설명하는 반론은 “불편이 없다”가 아니라 **그 불편이 별도 설치·승인·구독을 감수할 만큼 크지 않을 수 있다**는 것이다.
이를 해결하려면 맥락을 많이 저장한 수보다, 저장한 결정이 다음 업무에서 실제 적용된 횟수를 측정해야 한다.

## 범위와 비용

MVP 필수: 한 클라이언트의 실제 호출·조건 반영, 공통/프로젝트 경계, 출처·승인·대체/폐기, 안전한 잠금·삭제·복구, 오류 복귀와 첫 가치 안내.
그 다음: 실제 사용자가 실패한 색인 질의 보완, 승인 부담 축소, 해당 고객의 설치 흐름.
보류: 스토어 배포 자체를 성공 목표로 삼기, 모든 클라이언트 동시 지원, 검증 전 임베딩/서버 AI 비용 추가, 외형 중심 대시보드 확대.
수동 복사는 자동 MCP라는 합격 조건을 대체하지 못한다. 인터뷰에서 수동으로 문제를 설명받는 것은 가능하지만 제품 성공으로 집계하지 않는다.

단위경제성은 실측 자료가 없으므로 아래는 **가격 결정이 아닌 민감도 예시**다. 월 가격을 19,000원, 기타 서비스 원가를 1,000원,
지원 인건비를 시간당 30,000원으로 가정한다. 실제 요금·급여·원가가 아니며 부가세·결제 수수료·개발·판매·고정비를 제외했다.

| 사용자당 월 지원 시간 | 지원 비용 = 시간 × 30,000원 | 잔여 기여액 = 19,000 − 지원 − 1,000 | 해당 가정의 기여율 |
| --- | --- | --- | --- |
| 10분 | 5,000원 | 13,000원 | 68.4% |
| 30분 | 15,000원 | 3,000원 | 15.8% |

이는 순이익·실제 매출총이익률이 아니다. 로컬 연산으로 서버 비용이 낮아도 설치·복구 지원 시간이 수익성을 바꾼다.
CAC는 실제 획득 비용/신규 유료 고객, LTV는 관측된 유지·기여액이 필요하다. 지금은 계산할 근거가 없으며 투자금·가치평가·TAM도 제시하지 않는다.

## 사용자가 시간을 써야 하는 검증과 개발로 가능한 일

개발 환경에서 가능한 일: 코드·프로토콜·색인 사례 검증, 합성 금고 보안 재현/수정, 검토 보고서와 설치 안내, 회귀 검사.
사용자의 실제 기기/계정이 필요한 일: Codex 로그인 복구 후 새 세션 호출·출력, 신뢰 승인된 훅과 설치 가능한 Chrome 확장, 실제 고객 도구에서 연결 확인.
사용자가 고객과 해야 하는 일: 인터뷰 원문 확인, 파일럿 참여/동의 확보, 비교 작업·재방문·가격 선택 관찰. 지금 고객에게 메시지나 결제 요청을 보내지는 않았다.

남은 기간 반복 사용과 승인·절약 시간 기록 → 마지막에 기존 대안 대비 결과와 가격 선택으로 유지/수정 판단.

핵심 측정값: **일주일에 승인된 최신 조건을 실제 반영해 사용자가 수용한 프로젝트 재개 작업 수**.
