# 업무별 선호도 적용 조건

챕터26은 ‘캠페인에서는 실행안3개’ 같은 승인 조건이 단순 번역에도 적용되는 문제를 다룬다.
공통 기억을 먼저 읽고 **현재 명시 요청 > 선택 프로젝트 > 공통 기본값**을 유지하되,
각 기억이 현재 업무에 적용되는지 먼저 제한한다. 자연어의 모든 조건을 이해하는 기능은 아니다.

## 저장과 조회 계약

`propose_memory`에 선택적 `applicability.taskTypes`를 전달한다. 지원 값은 `writing`(문안 작성),
`translation`(번역), `campaign`(캠페인), `analysis`(분석), `coding`(개발)이며 중복 없는1~5개다.
사용자가 명시한 조건만 후보로 만들고 별도 로컬 검토에서 승인한다. 프로젝트 발언을 공통으로
승격하지 않으며 기존 비정형 문장을 자동 분석해 조건을 붙이지 않는다.

예시: 사용자가 명시적으로 공통 ‘캠페인 작업에서는 실행안3개’를 요청한 경우의 후보다.

```json
{
  "scope": { "type": "global" },
  "kind": "preference",
  "key": "format",
  "value": "실행안 3개를 제시",
  "applicability": { "taskTypes": ["campaign"] },
  "source": { "kind": "user", "reference": "local:user-input", "excerpt": "캠페인 작업에서는 실행안 3개를 제시해 줘" },
  "reason": "사용자가 명시한 업무별 선호"
}
```

조회는 `get_context({"taskType":"campaign"})`, 검색은
`search_memory({"query":"format","taskType":"campaign"})`처럼 현재 업무를 전달한다.
프로젝트가 있으면 확정된 UUID, 현재 명시 조건이 있으면 동일한 `requestConditions`도 매번 전달한다.
각 호출은 앞선 호출의 선택을 기억하지 않는다.

| 상황 | 적용 결과 |
| --- | --- |
| 조건 없는 공통 문장형 + 캠페인 전용 프로젝트 실행안3개, campaign 요청 | 프로젝트 실행안3개 |
| 같은 기억, translation 요청 | 공통 문장형. 프로젝트 조건의 본문·출처는 반환하지 않음 |
| 같은 기억, taskType 생략 | 공통 문장형. 모든 업무 한정 기억 제외 |
| campaign + 현재 요청에 format=표 하나 | 현재 요청 우선. 저장 기억은 변경하지 않음 |
| 후보·사용 중지·대체된 기억 또는 다른 프로젝트 | taskType이 맞아도 반환하지 않음 |

업무 필터는 프로젝트 덮어쓰기와 검색 순위보다 먼저 적용한다. 따라서 현재 업무에 해당하지 않는
프로젝트 기억이 유효한 공통 기본값을 가리지 않는다. taskType은 현재 요청을 근거로 AI가 선택하는
기능 입력이지 인증/권한 경계가 아니다. 캠페인 문안의 **번역 요청**은 번역으로 선택하며, 복합·모호한
요청은 생략하거나 확인한다. 제외된 기억을 모으려고 여러 종류를 순회하지 않도록 도구·스킬에 안내한다.

응답의 `taskType`은 선택 값 또는 null, `taskExcludedCount`는 선택 범위 내 active 기억 중 업무
조건 때문에 제외한 개수다. 질의 일치 개수나 누락 본문을 뜻하지 않으며 크기 제한의 `omittedCount`와
다르다. 다른 프로젝트의 개수는 포함하지 않는다. 반환한 조건에는 해당 applicability도 포함한다.
필터 개수는 색인 생성 때 집계하며 검색마다 전체 기억을 다시 순회하지 않는다.

## 로컬 검토와 변경

사용자 터미널의 `propose-task`에서 범위·값·쉼표 구분 업무를 입력하면 후보를 만든다. 기존
`propose`는 업무 제한 없는 후보를 만든다. `review`와 Chrome popup은 적용 업무를 표시하고,
교체 대상이 있으면 이전 기억의 적용 조건도 표시한다. 승인 전에는 조회에 적용하지 않는다.
후보 값 수정은 기존 적용 조건을 그대로 가진 **새 승인 대기 후보**다. 조건을 바꾸려면 새 후보를
명시적으로 제안하고 승인한다. 이미 같은 범위/key의 기억이 있으면 교체 대상을 명시해야 한다.

현재 같은 범위/key에는 active 기억 하나만 허용한다. 같은 key에 업무별 여러 값을 공존시키는
조건 분기 테이블은 구현하지 않았다. 서로 다른 key의 의미 충돌, ‘외부 고객일 때만’ 같은 임의 조건,
선호 강도 학습, 교정 뒤 결과 품질 계측도 별도 후속이다. 과거 조건부 자연어를 자동 변환하지 않으므로
해당 기억은 사용자가 검토해 명시 조건으로 교체해야 한다. 단순 수집 분류기가 이 필드를 자동 추론하지 않는다.

## 상태 전환과 검증

챕터26 당시 내부 기억 상태는 **v5**, 암호문 envelope은 기존 **v1/v2**다. v1~v4를 엄격히 파싱한 뒤 변환한다.
현재 상태와 전환 백업은 [챕터27 가져오기 계약의 v6](chat-history-import.md#데이터-버전과-검증)를 따른다.
옛 상태에 새 필드를 몰래 넣은 데이터는 거부한다. 기존 금고를 열면 첫 쓰기 전에 원래 암호문을
`pre-state-v5-<24자리 hex>.enc`로 보존한다. 옛 기억의 조건을 추측하지 않고 기존 동작을 유지한다.
Git revert로 사용자 데이터가 v4로 돌아가지는 않는다. 이전 코드가 필요하면 전환 전 백업과 당시
비밀번호/복구 파일을 이용해 새 디렉터리로 복원한다. 로컬 delete-all은 앱 관리 전환 백업도 지운다.
별도 export·복구 파일·원격 데이터는 [삭제/복구 안내](recovery-keys.md)를 따른다.

Codex/Claude 설치기의 `upgrade`는 알려진 이전 제품 스킬 원문을 갱신하고 사용자 편집본은 보존한다.
새 안내는 taskType을 조회·추가 검색에 일관되게 전달한다. 실제 사용자 기기에 설치한 것은 아니다.

검증: 전체 Node72/72, 실제 stdio MCP의 후보→로컬 승인→업무별 조회·검색/출처 제외,
v4 암호문 보존→v5 저장→export/restore 및 복구 파일 복원, 실제 PTY 제안/승인,
설치 업그레이드, 실제 Chromium의 합성 DOM/mock Chrome API 검토 화면을 통과했다.
전체 `npm run test:local` 통과. 2026-11-05 실제 `test:codex` 재시도는 인증 갱신401로 종료해
get_context0회/결과물 없음이다. 업무 선택을 포함한 실제 AI 개인화·사용자 만족도는 미검증이다.
