# Growth Brain 구현 스펙 — 챕터별 진행 기준

우선순위: 최신 사용자 요구사항 → 첨부 `writing-block.md`의 전략 → 기존 master_spec 1.0.
이 문서는 보드를 실행 가능한 단위로 구체화한다. ign8t의 기존 마스터 본문이 자동 갱신된 것은 아니다.
완료는 실제 소스와 검증으로 판단한다. 보드 상태만으로 과거 구현이 복구됐다고 간주하지 않는다.

## 공통 경계

- 사용자 기기에서 암호화·해독·검색한다. 개발 클라우드와 실제 사용자 기기를 구분한다.
- 암호화 대상: 프로젝트 이름, 원문, URL·출처, 선호도, 기억, 변경 사유, 수집 설정.
- MCP는 `get_context`, `search_memory`, `propose_memory`만 제공한다. 승인/잠금 해제/복구 키를
  모델에 전달하지 않는다. 후보 검토는 별도 사용자 터미널 또는 로컬 확장 popup에서 한다.
- 우선순위는 현재 명시 요청 > 프로젝트 조건 > 공통 기본값. 프로젝트 발언은 자동으로 global이 되지 않는다.
- 확장은 선택한 사이트·프로젝트의 대화를 수집한다. MCP가 전체 대화를 받는다고 가정하지 않는다.
- 같은 OS 사용자 권한의 프로그램은 열린 로컬 금고에 접근할 수 있다. 이 권한 경계를 샌드박스라고 주장하지 않는다.
- Supabase는 기존 프로젝트의 스키마를 읽기 전용으로 확인한 후 암호문 동기화에 재사용한다.

## 챕터 2 — 인증된 백업과 복원

입력: 사용자 터미널에서 지정한 백업 경로와 새 금고 디렉터리. 비밀번호는 비표시 터미널 입력.
출력: 동일 암호화 envelope의 파일(0600); 복원은 새 경로만 허용하고 기존 금고를 덮어쓰지 않는다.
백업은 원문 내보내기가 아니다. 복원 전에 암호 인증 및 전체 상태 불변식을 검증한다.

불변식: ID 유일, 프로젝트 참조 유효, global은 preference만, 같은 범위/key에 active 1개,
대체 관계는 같은 범위/key의 과거 레코드를 참조하는 비순환 그래프. 오류 시 현재 금고 보존.
검사: 백업 내용 평문 부재, 재복원, 오입력/변조/소유자 불일치, 기존 경로 덮어쓰기 거부,
손상된 그래프/중복 active의 복원 거부. Git revert는 사용자 데이터·외부 상태를 복원하지 않는다.

## 챕터 3 — 동의 기반 캡처 엔진

사이트: `chatgpt.com`, `claude.ai`만 초기 지원. 사이트별 enabled/projectId를 암호화 상태에 저장한다.
입력: site, projectId, conversation URL, message ID, role(user/assistant), text.
URL은 HTTPS 및 사이트 일치를 검증하고 query/hash를 제거한다. 확장 백그라운드는 sender.tab.url과 대조한다.
엔진은 사이트 동의와 프로젝트 일치를 다시 검사한다. 잠기면 소켓은 거부하고 평문 재전송 큐를 저장하지 않는다.

레코드: capture ID, projectId, site, canonical URL, message ID, role, text, content hash,
capturedAt, previousId(편집 revision). 같은 메시지+본문 재전송은 중복이고, 같은 메시지의 본문 변경은 새 revision이다.
원문·해시·출처는 모두 암호화 금고 안에 있다. 캡처 5,000개 및 금고 전체 16 MiB 상한을 유지한다.

규칙은 사용자 발언에서 명시 언어·어조·금지 표현을 보수적으로 추출하여 프로젝트 후보만 만든다.
assistant 원문은 저장할 수 있지만 사실 후보 자동 생성은 하지 않는다. 분류되지 않은 사용자 원문은
수동 검토용 피드백 후보로 남길 수 있다. 기존 확정 기억의 교체는 사용자가 검토한다.
검사: 중지·타 프로젝트·URL 위조·미승인 사이트·중복·편집·AI 발언·기억 범위·암호화 재시작.

## 챕터 4 — Chrome 연결과 최소 관리 UI

Manifest V3, 선택적 사이트 권한, 사이트별 adapter, content script, background, popup으로 나눈다.
권한·프로젝트·중지·후보 승인/기각은 extension popup만 변경한다. content script는 capture 요청만 보낸다.
페이지에 입력창 주입을 구현하지 않는다. popup은 textContent로 비신뢰 원문을 렌더링한다.
브라우저 storage에는 enabled와 불투명 project UUID만 저장하고 프로젝트 이름·원문·기억을 저장하지 않는다.

브라우저↔로컬 프로세스: Chrome native messaging 길이 프레임(JSON). host는 allowed_origins의
정확한 extension ID만 등록한다. 비밀번호/복구 키 필드는 없으며 금고는 별도 터미널에서 연다.
native 관리 API와 제품 MCP 도구 목록은 구분한다. 같은 사용자 OS 권한이라는 경계는 유지한다.
기존 native host와 MCP 설정을 덮어쓰지 않는 설치·해제를 제공한다.

검사: 실제 native stdio framing, 파일 암호화, 실제 Chromium의 확장 UI/배경 스크립트와 합성 DOM.
합성 DOM 검증을 실제 ChatGPT/Claude 로그인 사이트에서의 검증으로 보고하지 않는다.
DOM 선택자는 실제 서비스 변경에 취약하므로 매칭 실패는 빈 캡처로 중단하고 전체 페이지를 수집하지 않는다.

## 챕터 5 — 통합 증거 및 외부 선행 조건

한 챕터가 끝나면 관련 검사를 실행하고 커밋→푸시→원격 SHA 확인을 한다. 보드에는 실제 범위와
미검증 조건을 적는다. 전체 검사는 마지막에 변경된 경로에 대해 실행한다.

현재 외부 선행 조건:

- Codex CLI 인증 복구 후 실제 모델이 MCP를 호출하고 조건을 적용한 결과물 생성.
- Supabase 안전한 연결로 현재 스키마·RLS·준비 버전 점검.
- 사용자 기기와 실제 AI 사이트의 동의 기반 수집, 실제 사용자 개인화 A/B 검증.
- 첫 실제 클라이언트 흐름이 검증된 뒤 Claude Code 지원을 확장한다.

이 조건이 충족되지 않으면 관련 작업은 blocked 또는 검증 대기로 남기며 MVP 전체를 done으로 표시하지 않는다.

## 챕터 6 — 로컬 복구 키와 비밀번호 분실 복구

기존 envelope v1을 계속 지원하고 사용자 명시 발급 시 v2 키 포장으로 전환한다.
256비트 데이터 키를 비밀번호 유도 키와 별도 256비트 복구 키로 각각 AES-GCM 포장하며
본문 AAD로 슬롯·소유자를 인증한다. 발급/복원/재발급은 MCP·native API에 노출하지 않는다.

복구 파일은 사용자 터미널에서 별도 개인 경로에 배타적으로 저장한다. 저장소·금고 내부·
기존 파일·심볼릭 링크를 거부한다. 파일의 비밀값을 출력하지 않는다. 복원은 새 경로/새 키/
새 비밀번호만 허용하며 이전 백업은 변경하지 않는다. 키 재발급은 과거 백업까지 폐기하지 않는다.
자세한 사용·검증·롤백 계약은 [recovery-keys.md](recovery-keys.md)를 따른다.

## 챕터 7 — 수집 재개와 비동기 경계

배치를 시작할 때 대화 URL을 고정하고, 응답 사이마다 페이지·동의 세대가 같은지 확인한다.
중지/재개/페이지 이탈은 이전 작업의 응답을 새 작업의 중복 방지 기록으로 쓰지 않는다.
전송 중 마지막 DOM 변경도 다시 읽는다. BFCache 복원 시 관찰과 수집을 다시 시작한다.

금고 잠금/로컬 연결 부재는 1초부터 최대 30초까지 재시도한다. 원문을 디스크에 큐잉하지 않고
현재 DOM을 다시 읽는다. 권한·금고 동의 거부는 중단하며 용량/입력 오류는 무한 재시도하지 않는다.
사용자가 이미 탭을 닫았거나 페이지가 원문을 제거한 경우 수집을 보장하지 않는다.

popup의 수집 동의와 실제 전송 확인을 구분한다. 전송 결과는 사이트별 시각·성공/실패·중복 여부만
확장 워커 메모리에 보관하며 재시작 시 사라진다. 프로젝트 변경 전 응답을 새 프로젝트의 성공으로
표시하지 않는다. 프로젝트 검토 선택을 바꿔도 수집 대상은 새 동의 전까지 이전 설정임을 표시한다.
검증: 결정론적 IPC 경계 검사와 실제 Chromium 합성 DOM. 설치 확장/live AI 사이트 검증과 구분한다.

## 챕터 8 — 후보 수정과 확정 기억 사용 중지

사용자 전용 popup/native 또는 터미널에서만 `correct_candidate`와 `retire_memory`를 제공한다.
MCP 목록은 기존 세 도구를 유지한다. 페이지 content script는 두 관리 동작을 호출할 수 없다.

수정은 같은 범위·종류·조건 key·원래 출처를 유지하는 새 candidate를 만들고 `correctionOf`로
이전 후보를 연결한다. 이전 후보는 rejected로 남는다. 값과 수정 사유는 사용자가 입력하며,
현재 결정 교체는 이후 별도 승인 시 명시해야 한다. 프로젝트 발언의 global 승격은 없다.

사용 중지는 active만 retired로 바꾸고 사유·시각을 기록한다. 원문/이력의 물리 삭제 기능이 아니다.
전체 로컬 삭제는 기존 `delete-all` 흐름을 사용한다. retired는 조회/검색/승인에서 제외하며
superseded 결정을 다시 활성화하지 않는다. 프로젝트 조건 중지 후 공통 기본값이 적용될 수 있다는
점을 확인 UI에 명시하고, 공통값 중지는 모든 프로젝트에 영향을 준다고 표시한다.

내부 상태 v3: v1/v2는 검증 후 메모리에서 변환하고 다음 저장 시 기록한다. 암호문 envelope의
v1/v2와 독립이다. 수정 참조는 같은 범위/key/종류의 이전 rejected 항목이어야 하며, retired에는
사유·시각·이전 승인 증거가 필요하다. 이전 코드로 돌아가기 전에 전환 전 백업을 보존한다.
검증은 엔진 불변식, 실제 native→MCP 조회, 합성 Chromium popup 및 실제 PTY를 포함한다.

## 챕터 9 — 추가 검색의 현재 요청 우선순위

`search_memory`에 선택적 `requestConditions`를 추가한다. `get_context`와 같은 유효 기억
선별기를 사용하며 현재 요청으로 덮어쓴 key는 검색 대상에서도 제외한다. 현재 요청의 값은
`get_context`에서만 `current_request`로 반환하고 검색에서 승인 기억으로 가장하지 않는다.
현재 요청은 저장하지 않으며 호출마다 전달한다. 이전 호출이나 다른 세션의 조건을 재사용하지 않는다.

응답 개수/크기와 `omittedCount`는 적용 가능한 승인 기억만 대상으로 계산한다. 후보·사용 중지·
대체 기억·다른 프로젝트는 계속 제외한다. 50개 조건 제한과 입력 검증을 두 도구에 공통 적용한다.
MCP 도구는 세 개를 유지하며 상태 v3/envelope v1/v2 형식은 바꾸지 않는다.
엔진 회귀 재현과 실제 stdio MCP에서 전달·잠금 거부·암호문 파일 불변을 검증한다.

## 챕터 10 — Codex 스킬 갱신과 사용자 설정 보존

`codex-integration.py upgrade`로 이미 설치된 스킬을 갱신한다. 현재 소스 또는 저장소에서
확인한 이전 배포본의 SHA-256과 일치하는 내용만 소유 파일로 인정한다. 사용자 편집본과
알 수 없는 이전 버전은 자동으로 합치지 않는다. `install`의 기존 덮어쓰기 거부는 유지한다.
갱신은 같은 디렉터리에서 임시 파일 쓰기/fsync 후 원자적 교체로 완료한다. 실패 시 이전 파일을
유지하고 임시 파일을 정리한다. 업그레이드/해제 모두 기존 옵션과 소유권을 확인한다.

MCP 소유권은 command/args/socket뿐 아니라 추가 환경변수·전달 변수·cwd·도구 허용/차단·
timeout·enabled·알 수 없는 필드까지 검사한다. 사용자 변경이 있으면 설치/갱신/해제를 모두
거부해 수정 내용을 보존한다. 스킬 심볼릭 링크와 별도 파일도 보존한다. 실제 금고는 열지 않는다.
검증은 실제 파일/프로세스와 mock Codex CLI로 수행하며 실제 Codex 모델 세션과 구분한다.

## 챕터 11 — Codex/Claude Code 자동 수집

최신 사용자 지시에 따라 두 클라이언트의 공식 입력/최종 답변 훅을 공통 로컬 엔진에 연결한다.
상태 v4에 암호화된 작업 디렉터리-프로젝트 동의, 클라이언트/세션/턴/역할 캡처를 추가한다.
동의 세대/세션 프로젝트/선행 입력 검증을 통해 늦은 응답의 다른 프로젝트 유입을 막는다.
공통 자동 승격이나 자동 승인 없이 사용자 피드백 후보만 생성한다. 자세한 설치·중지·검증과
클라이언트 신뢰 검토 및 잠금 중 누락 한계는 [agent-capture.md](agent-capture.md)를 따른다.

상태 전환 전에 기존 인증 암호문을 보존한다. v4의 projectTriggers는 다음 챕터의 명시적
사용자 라우팅 설정을 위한 빈 구조로 준비하며 현재 동작에 키워드 자동 추론을 넣지 않는다.

## 챕터 12 — 공통 중심 색인과 명시 트리거

상태 v4의 projectTriggers를 활성화하고 공통/프로젝트별 RAM 역색인을 분리한다. 프로젝트 없이도
공통 조회가 가능하다. 명시 프로젝트 또는 단일 사용자 등록 키워드에만 프로젝트 색인을 조회하며,
복수 일치는 공통만 반환하고 선택을 요구한다. 조건 우선순위는 현재 요청 > 프로젝트 > 공통이다.
승인 active의 key/value만 정규화·한글 글자쌍·제한된 조사/조건명 별칭으로 색인하고 BM25 기반
순위를 반환한다. 과거값을 인용한 provenance는 근거로만 반환한다. 상태 변경/쓰기 롤백/잠금의
캐시 수명과 실제 MCP 통신을 검사한다. 설치 스킬과 두 훅의 안내도 공통 중심 조회로 갱신한다.
상태/envelope 버전은 더 바꾸지 않는다. 구조와 재현 평가/한계는 [memory-index.md](memory-index.md)를 따른다.

## 챕터 13 — 후보 추출 정밀도

2026-11-04 사용자의 품질 최적화 요청을 반영한다. 질문/인용/일회성/미확정 표현을 보수적으로
제외하고 명시 조건을 안정된 key로 분리한다. 부정·단위·기간을 보존하고 긴 문장의 절단을 피한다.
전체 원문은 캡처에 보존하며 후보는 프로젝트 범위·사람 승인 조건을 유지한다. 기존 저장 데이터
재분류/버전 변경은 없다. [평가와 한계](memory-quality.md)를 따른다.

## 챕터 14 — 개념 보조와 검색 비용

어휘/BM25와 8개 정형 조건의 제한된 한국어/영어 질의 패턴을 결합한다. 승인 기억의 key만
개념 색인에 넣고 출처/과거값/범위를 의미 추론으로 확장하지 않는다. 결과에 단어와 개념 일치
근거를 구분한다. 검색마다 전체 유효 기억 Map을 복제하지 않고 posting 후보에 우선순위 필터를
적용한다. 기존 단어 검색과 현재 요청>프로젝트>공통 규칙, 잠금/상태 전이는 유지한다.
동일 확대 corpus의 전후 Top1/recall/음성 오탐, 준비 후 반복 성능, 실제 MCP를 검증한다.
외부 모델·임베딩·평문 디스크 색인은 없으며 일반 의미 이해로 보고하지 않는다.

## 챕터 20~22 — 제품 실사와 개인정보 수명주기

고정 공개 스킬 검토로 [제품 실사](product-diligence-2026-11-04.md)와 [위협 모델](growthbrain-threat-model.md)을 작성했다.
실제 인터뷰/합성 페르소나/개발 검사를 구분하고 고객군·유료 수요는 가설로 남긴다.
잠금은 금고의 새 접근을 먼저 차단하고 열린 IPC 연결을 종료한다. 로컬 삭제는 명시 확인 뒤
현재 금고 및 앱 관리 전환 백업에 적용하며 수동 export/복구 파일/원격/AI 보유 맥락은 별도다.
파일 사전검사 실패/부분 삭제는 완료로 표시하지 않고 잠근다. 상태 v4와 envelope v1/v2는 변경하지 않는다.

2026-11-04에는 후속 우선 검증을 **맥락 인계**로 정리했다. 현재 get_context의 승인 조건/출처/이유 전달과
목표·완료/진행/차단·다음 행동의 최신성/근거가 검증된 인계를 구분한다. 전용 상태 계약과 실제
세션 A→B 작업 재개는 아직 구현/검증 완료가 아니다. 장기 선호도와 다른 생명주기를 설계하고
기존 승인·범위·명시적 대체 규칙을 유지해야 한다.

## 챕터 24 — 선호도 개인화 목표와 비교 기준

2026-11-05 최신 사용자 결정은 **선호도에 맞는 AI 결과가 최상위 목표**라는 것이다.
인계는 이 결과를 다음 세션·프로젝트·AI에도 이어 주는 수단으로 배치한다.
[공식 경쟁 자료/실제 소스 대조](preference-personalization-review-2026-11-05.md)와
[실험·합격 기준](personalization-evaluation.md)을 추가했다. 이 챕터는 제품 기능 구현 완료가 아니다.

후속 설계: 승인한 공통 기본값을 먼저 검토→업무별 적용/예외→선택 프로젝트→현재 요청 우선→
실제 결과→교정 후보/승인→다음 작업 평가. 기존 상태 v4와 envelope v1/v2는 변경하지 않는다.
현재 같은 key의 범위 우선순위와 업무 의미에 따른 적용/상충 해소를 혼동하지 않는다.
잘 작성한 고정 프로필을 주 대조군으로 두고 채택/교정·관리 비용을 측정한다.
단일 North Star 제안은 주간 선호도 재설명 없이 채택한 작업 수이며 아직 계측하지 않았다.
