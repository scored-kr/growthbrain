# 로컬 복구 키와 비밀번호 분실 복구

계정 로그인 비밀번호와 로컬 금고 비밀번호는 별개다. 이 기능은 로컬 금고만 복구하며,
Supabase 계정 재설정이나 서버 동기화를 구현한 것은 아니다. 모든 명령은 사용자가 자신의
기기의 터미널에서 실행한다. AI가 접근하는 클라우드에 실제 사용자 키를 발급하지 않는다.

## 사용 순서

1. 열린 금고 터미널에서 `lock`으로 종료한다. 전환 전 암호문 백업을 보관한다.
2. `npm run vault -- recovery /absolute/vault-directory`를 실행한다.
3. 현재 비밀번호를 비표시 입력하고 `ISSUE`로 확인한다. 별도 0700 개인 디렉터리의 새 파일
   경로를 입력한다. 키는 0600 파일에만 저장하며 터미널에도 출력하지 않는다.
   금고 내부·Git 작업 트리·기존 파일·심볼릭 링크에는 발급하지 않는다.
4. `npm run vault -- serve /absolute/vault-directory`로 다시 열고 `backup`으로 **새 암호문 백업**을
   저장한다. 복구 키 발급 전의 백업에는 새로운 복구 기능이 소급 적용되지 않는다.
5. 복구 파일은 백업과 분리된 안전한 오프라인 장소에 보관한다. 파일을 채팅·MCP·로그·저장소에
   넣지 않는다. `.recovery`는 Git 제외 규칙으로도 막지만 파일 이름만으로 보안이 보장되지는 않는다.

비밀번호를 잃었을 때:

```sh
npm run vault -- recover /absolute/new-vault-directory /absolute/private-backup.enc
```

사용자 전용 터미널에서 복구 파일의 경로와 새 비밀번호를 입력한다. 키 내용을 복사할 필요가 없다.
인증과 상태 검증을 통과한 뒤 새 디렉터리에만 복원한다. 원본 금고·백업·복구 파일은 변경하지 않는다.
새 데이터 키와 비밀번호로 저장하며 이전 복구 권한은 이 새 금고에 가져오지 않는다.
필요하면 새 금고에서 새 복구 파일을 발급하고 다시 백업한다.

## 암호화 계약

- 기존 envelope v1은 AES-256-GCM과 scrypt(N=32768,r=8,p=1)로 계속 읽고 쓸 수 있다.
  복구 발급은 명시적인 v2 전환이다. 내부 기억 상태 버전과 암호문 envelope 버전은 별개다.
- v2 데이터 키는 무작위 256비트다. 비밀번호에서 유도한 키와 무작위 256비트 복구 키가 각각
  데이터 키를 AES-GCM으로 포장한다. 각 저장/포장에는 새로운 96비트 nonce를 사용한다.
- 포장 AAD는 버전·owner ID·용도(password/recovery)를 묶는다. 본문 AAD는 정규화된 헤더와
  두 슬롯을 인증하므로 슬롯 삭제/교체/다른 회원 이식도 거부한다.
- 복구 재발급 시 데이터 키도 교체한다. 이전 키는 새 스냅샷을 열 수 없지만 이미 보관한 과거
  백업은 여전히 열 수 있다. 재발급은 외부 사본의 접근 권한을 소급 폐기하지 않는다.
- 파일 발급을 먼저 완료하고 금고를 원자적으로 교체한 다음 메모리의 키를 교체한다.
  발급/저장 실패는 기존 금고를 유지한다. 프로세스 중단 시 사용되지 않는 복구 파일이 남을 수
  있으므로 성공 출력과 새 백업 복원 검증을 확인한다. 자동으로 기존 파일을 삭제/덮어쓰지 않는다.
- 복구 파일 자체는 비밀이다. 파일을 가진 같은 OS 사용자의 프로그램으로부터 이를 숨기지 않는다.
  AI에 셸 권한이 있으면 같은 계정의 파일을 읽을 수 있으므로 사용자 기기의 신뢰 경계를 지켜야 한다.
- 키 버퍼는 지우지만 JS 문자열/힙의 모든 복사본 소거를 보장하지 않는다. 암호화 독립 보안 감사는 남아 있다.
- 복구 파일과 비밀번호를 모두 잃으면 복원할 수 없다. 서버나 운영자 우회 키는 없다.

## 확인 범위

`test/recovery.test.mjs`: v1 호환, v2 비밀번호 복원, 키 분실 복구, 재발급/과거 백업, 변조·소유자·
권한·경로 방어, 재시작, 동시 저장, 로컬 IPC에 복구 API 부재를 확인한다.
`npm run test:recovery`: 실제 PTY에서 발급→백업→새 비밀번호 복구→재시작, 키·비밀번호 비출력을
합성 데이터로 확인한다. 사용자 기기의 오프라인 보관이나 실제 계정 복구 검증으로 보고하지 않는다.

envelope v2 지원 전 코드로 `git revert`하면 v2 파일을 읽을 수 없다. 전환 전 v1 암호문 백업과
그 비밀번호를 별도 보존한다. Git 커밋은 사용자 데이터나 복구 키를 백업하지 않는다.

챕터26의 내부 기억 상태 v5 전환은 envelope v1/v2와 별개다. v1~v4 기존 금고를 열 때 첫 쓰기 전
원래 암호문을 `pre-state-v5-<24자리 hex>.enc`로 보존한다. 이 백업은 당시 비밀번호/복구 파일로
열어야 하며 이후 비밀번호·복구 재발급이 과거 사본의 권한을 바꾸지 않는다. v5를 모르는 이전 코드로
돌아갈 때에는 전환 전 백업을 새 디렉터리에 복원한다. [조건/전환 검증](preference-applicability.md)을 참고한다.

`delete-all`의 명시적 DELETE 확인은 현재 로컬 금고와 앱이 관리하는 같은 디렉터리의
`pre-state-v<버전>-<24자리 hex>.enc` 전환 백업에 적용된다. 사용자가 내보낸 백업·개인 복구 파일·
외부/OS 백업·원격 계정 데이터·AI가 받은 맥락은 남는다. 과거 백업과 해당 복구 파일을 함께
보유하면 그 과거 상태를 계속 복구할 수 있다. 삭제 범위·실패 처리는 [로컬 안내](local-development.md)를 따른다.

챕터27의 현재 내부 상태는 **v6**다. v1~v5 전환 전 백업은 pre-state-v6 이름으로 보존하며
챕터26의 v5 전환 설명은 당시 기록이다. envelope v1/v2는 변하지 않는다. 가져온 양쪽 일반 채팅의
출처/분기 표시도 암호화/복구 대상이다. [현재 가져오기·전환 계약](chat-history-import.md)을 참고한다.
